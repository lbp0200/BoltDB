## 1. Connection Lifecycle

### 1.1 状态结构

每个客户端连接由一个 `connState` 结构体表示（`internal/server/handler.go:26`）：

```go
type connState struct {
    mu              sync.Mutex
    ctx             context.Context
    cancel          context.CancelFunc

    inTransaction   bool
    commands        []TransactionCommand
    transaction     *TransactionState
    clientInfo      *ClientInfo
    clusterAsking   bool
    watchedKeys     map[string]struct{}
    dirtyKeys       map[string]struct{}
    subscriber      *store.Subscriber
    monitoring      bool
    monitorCh       chan []byte
}
```

### 1.2 生命周期状态机

```
TCP Accept
    │
    ▼
handleConnection(conn)
    │
    ├─ connState{ctx, cancel}       ←  per-connection context
    ├─ registerConnection()          ←  conns map, connMeta, ClientInfo
    ├─ bufio.NewReader / Writer
    ├─ TCP_NODELAY
    │
    ▼
┌─────────────────────────────────────────┐
│        命令处理主循环                    │
│                                         │
│  for {                                   │
│    ReadRESP() → processRequest()         │
│    Pipeline: drain buffered commands     │
│    batch WriteRESP() + Flush()           │
│    outputBytes tracking                  │
│    check OutputBufferLimit                │
│    ↓ if subscriber != nil                 │
│    runPubSubLoop()                       │
│    ↓ if monitoring == true                │
│    runMonitorLoop()                      │
│  }                                       │
└─────────────────────────────────────────┘
    │
    ▼ cleanup (defer chain)
    ├─ cancel()                    ←  ctx.Done() → unblock all blocking ops
    ├─ unregisterConnection()       ←  remove from conns map
    ├─ RemoveSubscriber(sub)        ←  PubSub cleanup
    ├─ unregisterMonitorClient()
    ├─ unwatch all watched keys
    └─ conn.Close()
```

### 1.3 关键语义

| 阶段 | 行为 |
|------|------|
| **Context 继承** | `parentCtx = h.Ctx`（服务器级），fallback `context.Background()`。`connState.ctx` 由 `context.WithCancel(parentCtx)` 派生。服务器关闭 → 所有连接 ctx 取消 |
| **Pipeline** | 先读第一个命令，然后 `reader.Buffered() > 0` 时 drain 剩余命令。所有响应批量 flush |
| **PubSub 模式** | 命令处理主循环检测 `subscriber != nil` → 切换到 `runPubSubLoop()`（goroutine: ReadRESP → chan + flush ticker 100ms）。退出条件：ctx.Done / QUIT / read error / output buffer limit |
| **MONITOR 模式** | 类似 PubSub，切换到 `runMonitorLoop()`。仅接受 QUIT/PING。`broadcastToMonitors()` 在 `processRequest()` 中同步调用 |
| **PSYNC 接管** | `processRequest()` 检测 PSYNC → `handlePSyncWithRDB()` 返回 `ReplicationTakeoverSignal` → 主循环退出，连接由复制 goroutine 管理 |
| **CLIENT KILL** | 调用 `state.cancel()` → ctx 取消 → 主循环/read 阻塞退出 → cleanup chain 执行 |
| **connState nil** | `executeCommand()` 中 `panic("nil connState")` — fast-fail，无 fallback |

### 1.4 并发安全

| 资源 | 保护机制 |
|------|---------|
| connState 字段 | `state.mu`（Mutex），读多写少字段用 atomic |
| conns 注册表 | `h.connsMu`（RWMutex） |
| watchMonitors | `h.watchMu`（Mutex） |
| monitorClients | `h.monitorMu`（Mutex） |

## 2. Replication Model

### 2.1 角色

- **Master**: 接受写入，传播命令到 Slave，维护 backlog
- **Slave**: 连接 Master，接收并执行复制命令，自动重连

由 `ReplicationManager`（`internal/replication/replication.go:19`）管理。

### 2.2 Offset 语义

```
Master Repl Offset:
    单调递增的字节计数器
    每传播一个 RESP 命令：offset += len(serialized RESP)
    每个 Slave 维护自己的 ACK offset

Backlog Offset:
    backlog 是环形缓冲区（size = 1MB 默认，最大 512MB）
    写入位置：offset % size
    可用范围：[current_offset - size, current_offset)
```

### 2.3 从节点状态机

```
Disconnected
    │  StartSlaveReplication()
    ▼
Connecting
    │  TCP dial → sendHandshake()
    ▼
Syncing
    │  PSYNC → FULLRESYNC → RDB load
    ▼
Connected
    │  readCommandLoop() — 持续接收并执行复制命令
    │  ↓ 连接断开
    ▼
Disconnected → backoff → Connecting → ...
```

### 2.4 自动重连（SlaveReconnector）

位于 `internal/replication/reconnect.go:42`

| 参数 | 值 |
|------|-----|
| Base backoff | 1s |
| Max backoff | 60s |
| 退避策略 | Exponential: 1s → 2s → 4s → ... → 60s |
| 重置条件 | 稳定连接 ≥ 30s 后重置重试计数 |
| 重连方式 | PSYNC 使用 `lastReplId lastOffset`（增量重连，非全量） |

### 2.5 握手流程

```
Slave → Master:
  PING
  REPLCONF listening-port 6380
  REPLCONF capa eof
  REPLCONF capa psync2
  PSYNC <replId> <offset>

Master → Slave:
  +FULLRESYNC <replId> <offset>  → 全量同步（RDB）
  +CONTINUE <replId>              → 增量同步
```

### 2.6 Backlog API

`internal/replication/backlog.go:12`

```go
Append(data []byte) int64           // 写入，返回 startOffset
GetRange(start, end int64) ([]byte, error)
GetCurrentOffset() int64
GetSize() int64
GetAvailableLength() int64          // 可用数据字节数
AvailableStartOffset() int64        // 最早可用偏移量
IsOffsetAvailable(offset int64) bool
```

- 当 `dataLen >= size` 时：只保留最后 size 字节
- 当 `dataLen < size` 时：环形写入（offset % size）
- `GetRange()` 校验：offset 不过旧（≥ availableStart），不过新（< currentOffset）

### 2.7 资源生命周期

```
ReplicationManager.Stop():
    close(stopCh)
    close all slave connections
    close master connection
    slaveReconnector.Stop()  // close(stopCh) + TCP close + wg.Wait()
```

## 3. Propagation Semantics

### 3.1 传播规则

写命令在 `processRequest()` 中检测并传播（`handler.go:492`）：

```go
if h.Replication != nil && h.Replication.IsMaster() && isWriteCommand(cmd) {
    if cmd != "REPLICAOF" && cmd != "PSYNC" && cmd != "REPLCONF" {
        h.Replication.PropagateCommand(req.Args)
    }
}
```

**传播条件：** 主节点 + 写命令 + 非复制控制命令。

### 3.2 写命令列表

完整列表见 `internal/server/replication_helper.go:5`，分类如下：

| 类别 | 命令 |
|------|------|
| **String** | SET, SETEX, PSETEX, SETNX, GETSET, MSET, MSETNX, INCR, INCRBY, DECR, DECRBY, INCRBYFLOAT, APPEND, SETRANGE, SETBIT, BITOP, BITFIELD |
| **Generic** | COPY, DEL, EXPIRE, EXPIREAT, PEXPIRE, PEXPIREAT, PERSIST, RENAME, RENAMENX |
| **List** | LPUSH, RPUSH, LPOP, RPOP, LSET, LTRIM, LINSERT, LREM, RPOPLPUSH, LPUSHX, RPUSHX, LMOVE, BLMOVE, BRPOPLPUSH, BLPOP, BRPOP |
| **Hash** | HSET, HDEL, HMSET, HSETNX, HINCRBY, HINCRBYFLOAT |
| **Set** | SADD, SREM, SPOP, SMOVE, SINTERSTORE, SUNIONSTORE, SDIFFSTORE |
| **Sorted Set** | ZADD, ZREM, ZINCRBY, ZPOPMAX, ZPOPMIN, ZREMRANGEBYRANK, ZREMRANGEBYSCORE, ZREMRANGEBYLEX, ZUNIONSTORE, ZINTERSTORE, ZDIFFSTORE, ZRANGESTORE |
| **HyperLogLog** | PFADD, PFMERGE |
| **Geo** | GEOADD, GEOSEARCHSTORE |
| **Stream** | XADD, XDEL, XACK, XCLAIM, XGROUP, XTRIM |
| **JSON** | JSON.SET, JSON.DEL, JSON.ARRAPPEND, JSON.NUMINCRBY, JSON.NUMMULTBY, JSON.CLEAR |
| **TimeSeries** | TS.CREATE, TS.ADD, TS.DEL |

### 3.3 MULTI/EXEC 传播

`handler.go:5062-5071`：

```
MULTI + 多个写命令 → EXEC:
    for each command in transaction:
        if isWriteCommand(cmd):
            h.Replication.PropagateCommand(fullArgs)  // 逐个传播
```

每个写命令作为独立 RESP 传播到 Slave（不是作为 MULTI/EXEC 块传播）。

### 3.4 传播流程

```
PropagateCommand(cmd):
    1. serializeCommand(cmd) → RESP wire bytes
    2. backlog.Append(cmdBytes) → 写入环形缓冲区
    3. for each slave:
        if slave.IsReady():
            slave.SendCommand(cmdBytes, offset)
    4. IncrementReplOffset(len(cmdBytes))
```

**不传播的命令：** REPLICAOF, PSYNC, REPLCONF, MONITOR（monitor 广播而非复制传播），以及所有只读命令（GET, EXISTS, TYPE 等）。

## 4. Output Buffer Semantics

### 4.1 设计目标

保护服务器不被慢客户端拖垮。当连接的待发送数据超过硬限制时断开连接。

### 4.2 配置

```go
Handler.OutputBufferLimit int64  // 字节，0 = 不限制
```

通过 CLI flag `-client-output-buffer-limit` 设置。

### 4.3 追踪机制

`connMeta.outputBytes`（`handler.go:79`）累计跟踪：

```
每次 Flush 后：
    flushBytes = writer.Buffered()  // pre-Flush 值
    outputBytes += flushBytes
```

**重要：** `writer.Buffered()` 在 Flush **之前** 调用，否则始终为 0。

### 4.4 检查点

| 模式 | 检查时机 | 行为 |
|------|---------|------|
| **正常命令** | 每次 flush 后 | `if outputBytes > limit: return` → cleanup chain |
| **PubSub** | flush ticker（100ms） | 同，ticker 触发 flush + check |
| **MONITOR** | flush ticker（100ms） | 同 |

### 4.5 CLIENT LIST 输出

```
omem=<outputBytes>       // 累计发送字节数
oFlags=                  // 空：正常
oFlags=>                 // outputBytes > limit/2（接近限制警告）
```

### 4.6 超限处理

日志级别：WARN
记录：`remote_addr`, `output_bytes`, `limit`
动作：`return` → cleanup chain → `conn.Close()`
结果：连接断开，client 收到连接重置

## 5. Ownership Rules

### 5.1 Goroutine 拓扑

```
ServeTCP (Listener goroutine)
    │  Accept → go handleConnection(conn)
    │
    ├── handleConnection  ──── conn goroutine（每个连接一个）
    │       │
    │       ├── PubSub mode:  spawns reader goroutine
    │       │                  main goroutine: select loop
    │       │
    │       ├── MONITOR mode: spawns reader goroutine
    │       │                  main goroutine: select loop
    │       │
    │       └── PSYNC takeover: conn ownership → handleSlaveReplicationConnection
    │
    └── handleSlaveReplicationConnection ── slave goroutine（每个从节点一个）
```

### 5.2 资源所有权矩阵

| 资源 | 所属 goroutine | 跨 goroutine 安全？ | 保护机制 |
|------|---------------|---------------------|---------|
| `connState` 实例 | `handleConnection` | 部分字段 | `state.mu` (Mutex) |
| `connState.subscriber` | conn goroutine | 仅创建/销毁 | `state.mu` for read/write |
| `connState.monitorCh` | conn goroutine | 仅写 | `state.mu` + channel semantics |
| `connState.watchedKeys` | conn goroutine | 读不安全 | `state.mu` |
| `connState.inTransaction` | conn goroutine | 读不安全 | `state.mu` |
| `connState.transaction` | conn goroutine | 读不安全 | `state.mu` |
| `bufio.Reader/Writer` | conn goroutine | 否（独占） | 单 goroutine 保证 |
| `net.Conn` | conn goroutine | 否（独占） | 单 goroutine 保证 |
| `Handler.conns` | Handler (主控) | 是 | `h.connsMu` (RWMutex) |
| `Handler.watchMonitors` | Handler (主控) | 是 | `h.watchMu` (Mutex) |
| `Handler.monitorClients` | Handler (主控) | 是 | `h.monitorMu` (Mutex) |
| `Handler.PubSub` | Handler (主控) | 是 | `store.PubSubManager` 内部锁 |
| `ReplicationManager.slaves` | ReplicationManager | 是 | 内部锁 + atomic fields |

### 5.3 跨 goroutine 访问安全规则

```
connState.mu 保护:
    subscriber          — 设置/清除
    monitoring          — 设置/清除  
    monitorCh           — 设置/清除
    inTransaction       — 所有读写
    commands            — 所有读写
    transaction         — 所有读写
    watchedKeys         — 所有读写
    dirtyKeys           — 所有读写
    clusterAsking       — 所有读写

h.connsMu (RWMutex) 保护:
    conns[*connState]*connMeta     — RLock 读，Lock 写
    connMeta.outputBytes            — Lock 写（flush 后更新）
    connMeta.lastRead/lastWrite     — Lock 写

h.watchMu (Mutex) 保护:
    watchMonitors[key]     — markDirtyKeys 修改
    conn 的 watchedKeys     — cleanup 删除

h.monitorMu (Mutex) 保护:
    monitorClients 注册/注销

读写规则:
    connState 字段在所属 goroutine 内部可以直接读写（不加锁）
    跨 goroutine 访问 connState 字段必须先持有 state.mu
    conns 和 watchMonitors 必须通过 Handler 锁访问
```

### 5.4 所有权转移

| 场景 | 转移方式 | 说明 |
|------|---------|------|
| **PSYNC 接管** | `replicationOwned = true` | conn goroutine 阻止 defer close，由 `handleSlaveReplicationConnection` goroutine 负责关闭 |
| **CLIENT KILL** | 不转移，仅触发 cancel | 目标连接的 ctx 被取消 → goroutine 退出 cleanup |
| **PubSub reader** | spawn reader goroutine | reader goroutine 将请求通过 channel 发回主循环，done channel 保证退出同步 |

### 5.5 shutdown 顺序

```
Handler.Shutdown (或 Ctx cancel):
    1. Listener.Close()              → 停止 Accept
    2. for each conn: cancel()       → 所有连接 ctx.Done()
    3. 所有 conn goroutine 退出      → defer cleanup 执行
    4. ReplicationManager.Stop()    → slave goroutine 退出
    5. PubSubManager.Close()        → 清理订阅
    6. Db.Close()                   → BadgerDB 关闭
```

## 6. Cancellation Rules

### 6.1 取消传播链

```
服务器关闭 / 信号处理 (SIGTERM/SIGINT)
    │
    ▼
h.Ctx cancel (parent context)
    │
    ▼ (派生 cancel 链)
每个 connState.ctx cancel
    │
    ├── blocking ops:  select { case <-ctx.Done(): return }
    ├── PubSub loop:    select { case <-ctx.Done(): return }
    ├── MONITOR loop:   select { case <-state.ctx.Done(): return }
    └── slave loop:     select { case <-ctx.Done(): return }
```

### 6.2 阻塞操作取消契约

所有阻塞操作必须满足以下条件：

```go
// 必须模式：select 中包含 ctx.Done() 分支
select {
case result := <-opCh:
    return result
case <-ctx.Done():
    return nil  // 或 ErrClosed
}
```

| 操作 | 文件 | ctx 响应 |
|------|------|---------|
| **BLPOP/BRPOP** | `store/list.go:1500,1540` | `case <-ctx.Done()` |
| **BLMOVE/BRPOPLPUSH** | `store/list.go:1590,1637` | `case <-ctx.Done()` |
| **BZPOPMIN/BZPOPMAX** | handler (store 层) | `case <-ctx.Done()` |
| **XREAD (blocking)** | `store/stream.go:574,598` | `case <-ctx.Done()` |
| **PubSub loop** | `handler.go:683` | `case <-ctx.Done()` |
| **MONITOR loop** | `handler.go:994` | `case <-state.ctx.Done()` |
| **Replication loop** | `handler.go:1095` | `case <-ctx.Done()` |

### 6.3 CLIENT KILL 语义

```go
// handler.go — executeCommand 中 CLIENT KILL
state.cancel()  // → ctx.Done() → goroutine cleanup
```

CLIENT KILL 不会主动关闭连接，而是通过 `state.cancel()` 触发目标连接的 ctx 取消 → goroutine 退出 → defer cleanup chain 执行 → `conn.Close()`。

### 6.4 超时取消

阻塞操作支持 timeout 参数（单位：秒）：

```go
// handler 层解析 timeout 后派生 WithTimeout context
timeoutCtx, cancel := context.WithTimeout(ctx, time.Duration(timeout)*time.Second)
defer cancel()

// store 层使用 timeoutCtx 的 Done()
select {
case <-timeoutCtx.Done():
    // 超时 → 返回 nil（*-1\r\n）
case result := <-opCh:
    return result
}
```

超时返回 wire 格式 `*-1\r\n`（与 Redis 一致）。

### 6.5 取消安全性要求

```
1. 所有 goroutine 必须在 ctx.Done() 后 ≤ 1s 内退出
   (否则 Server.Shutdown 会 hang)

2. defer cancel() 必须在创建 ctx 的 goroutine 中

3. channel-based goroutine 通信必须使用 done channel:
   go func() {
       select {
       case result <- op():
       case <-done: return
       }
   }()

4. 禁止在退出路径中读写已被取消的连接
```

## 8. Cluster Module

### 8.1 架构

`internal/cluster/` — 单节点 cluster 原型（~800 生产行，~1000 测试行）。

```
Cluster 结构体:
    nodeID     string        // 40-char hex
    nodes      map[string]*Node
    slots      [SlotCount]*Node  // 16384 slots
    epoch      uint64
    mu         sync.RWMutex

Node 结构体:
    ID         string
    Addr       string
    Flags      NodeFlags  // master/slave/myself/fail
    Slots      SlotRangeList
    PingSent   time.Time
    PongRecv   time.Time
```

### 8.2 当前实现状态

| 功能 | 状态 | 说明 |
|------|------|------|
| Slot 计算（CRC-16/XModem） | ✅ | 含 `{hash_tag}` 支持 |
| Slot 分配 / ADDSLOTS | ✅ | 本地 slots 数组 |
| MOVED 重定向 | ✅ | `CheckSlotRedirect` |
| ASK 重定向 | ✅ | `RedirectError` + slot migration 状态 |
| CLUSTER INFO / NODES / SLOTS | ✅ | 信息查询命令 |
| CLUSTER MEET | ⚠️ Stub | 创建本地 Node 对象，不实际连接远程节点 |
| CLUSTER FORGET | ⚠️ Stub | 本地移除 Node |
| CLUSTER REPLICATE | ⚠️ Stub | 设置 role 不触发实际复制 |
| Slot 迁移（IMPORTING/MIGRATING） | ⚠️ Stub | 状态设置正确但无数据移动 |
| 配置持久化 | ⚠️ Stub | `handleSaveConfig` 返回 OK 但不写入 |
| 节点间 Gossip | ❌ 未实现 | 无 PING/PONG 消息交换 |
| 自动 Failover | ❌ 未实现 | `IsFailed()` 检测超时但不触发 |
| GETKEYSINSLOT / COUNTKEYSINSLOT | ✅ | 扫描 TYPE_ 记录计算 slot |

### 8.3 Cluster 状态机

```
Single-node (当前实现):
    CLUSTER MEET <addr:port> → 本地添加 Node（不连接）
    CLUSTER ADDSLOTS <slot> → 本地 slot 分配
    客户端请求命中非本地 slot → MOVED 重定向

Full cluster（目标状态）:
    Gossip 环 → 节点发现 → 配置 epoch 协商
    → 槽迁移 → 副本迁移 → failover 选举
```

### 8.4 设计约束

- Cluster 对 handler 是**可选的**：`handler.Cluster == nil` 时 cluster 命令返回 MOVED 重定向错误
- 每条命令 `processRequest → executeCommand` 前检查 slot 所有权（`CheckSlotRedirect`）
- `clusterAsking` 标志在 `connState` 中，仅在 ASK 重定向流程中使用
- Cluster **不引入新 state machine 状态**：cluster 模式下的 connection 仍然是 NORMAL

## 9. Sentinel Module

### 9.1 架构

`internal/sentinel/` — 内置 sentinel 原型（~1700 生产行，~2100 测试行）。

```
组件:
  sentinel.go      — 核心结构体：master 管理、run-id
  master.go        — 主观下线（SDOWN）/ 客观下线（ODOWN）检测
  failover.go      — 选举、副本提升、failover 编排
  gossip.go        — `__sentinel__:hello` channel gossip
  network.go       — TCP listener (sentinel 协议命令)
  handler.go       — PING / SENTINEL / INFO 命令响应
  config.go        — 配置管理
```

### 9.2 当前实现状态

| 功能 | 状态 | 说明 |
|------|------|------|
| Master 监控（PING） | ✅ | 周期性 PING，响应超时检测 |
| SDOWN -> ODOWN 状态机 | ✅ | 主观下线 → 客观下线转换 |
| Failover 选举 | ✅ | Leader 选举逻辑 |
| Gossip 协议 | ✅ | `__sentinel__:hello` PubSub channel 交换 |
| SENTINEL 命令 | ✅ | masters / master / get-master-addr-by-name 等 |
| TCP 命令监听 | ✅ | 独立 listener |
| Run-ID 生成 | ⚠️ Stub | `fmt.Sprintf("sentinel-%d", time.Now().UnixNano())`，非 40-char hex |
| Slave 完整实现 | ⚠️ Stub | `slave.go` 仅 22 行，信息结构体 |
| 配置持久化 | ⚠️ Stub | 运行时状态不持久 |

### 9.3 Sentinel 状态机

```
Master 检测状态:
    无故障: sentinel PING → +PONG
    SDOWN:  PING 超时（is-master-down-after-milliseconds）
    ODOWN:  多数 sentinel 同意 SDOWN（quorum）
    → ODOWN 触发 failover 选举
```

### 9.4 设计约束

- Sentinel 与 server **同进程**：通过 `handler.Sentinel` 访问，使用 store 的 PubSub channel 做 gossip
- Sentinel 不改变 connection 状态机
- 对 handler 是**可选的**：`-replicaof` 和 `-cluster` 不互斥，sentinel 通过独立二进制 `cmd/sentinel/main.go` 或内置模式运行

## 10. Entry Points

### 10.1 cmd/boltDB/main.go

BoltDB 服务器主入口。

```
Flag           Default        说明
───            ───────        ───
-addr          :6379          监听地址
-dir           /tmp/bolt_db   BadgerDB 数据目录
-log-level     info           日志级别
-cluster       false          启用 cluster 模式
-replicaof     ""             主节点地址（<host>:<port>），启用从节点模式
-skip-startup-cleanup false   启动时不清除过期数据
```

启动流程：

```
Parse flags → 初始化结构日志
  → BadgerDB.Open(dir)
  → Proto.NewHandler(db, opts...)
  → if cluster: cluster.NewCluster(db, nodeID, addr)
  → if replicaof: handler.StartSlaveReplication(addr)
  → handler.ServeTCP(addr)  // 阻塞
```

### 10.2 cmd/sentinel/main.go

独立 sentinel 进程入口。

```
Flag        Default       说明
───         ───────       ───
-addr       :26379        监听地址
-dir        /tmp/sentinel 数据目录
-monitor    ""            <master-name> <ip> <port> <quorum>
```

启动流程：

```
Parse flags → 初始化 store（BadgerDB）
  → sentinel.NewSentinel(db, opts...)
  → sentinel.ServeTCP(addr)
  → sentinel.StartMonitoring()
  → 阻塞
```

### 10.3 构建入口

```bash
go build -o ./build/boltDB cmd/boltDB/main.go       # 服务器
go build -o ./build/sentinel cmd/sentinel/main.go    # 独立 sentinel
```
